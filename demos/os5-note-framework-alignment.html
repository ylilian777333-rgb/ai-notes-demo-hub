OS5 · 笔记

用户痛点、方案与交互链路

三个场景：待办日程、想法随记、学习备考。每个场景先把用户在手机上真实卡住的地方一条条拆开，每条痛点配一个方案，再走一遍完整交互链路。最后由这些需求推出笔记的交互框架要怎么变。

2026-09-10内容助手对齐用
01

待办日程

用户不想在笔记里读待办。他只要知道现在该做什么、别错过时间。

痛点 1

记下来的那句话，不会变成一件会提醒你的事

开会时顺手记下"下周五之前把方案发给老王"。这句话留在会议记录的正文里，到了周五没有任何提醒——除非用户自己再打开待办应用，把这件事重录一遍。记录和待办是两套动作，用户要做两次。

方案

从记录里认出待办和时间，用户确认后落位

  • 录音、语音、图片、手写里的待办与时间自动认出来，用户点一下确认
  • 原话留在笔记里，认出的待办单独成条，两边关联：点待办能回到当时那句话
  • 顺带认出的地点、联系人、链接分发成可点卡片，跳系统应用

依赖 / 待定　置信度低于阈值不自动建，交用户确认；目标应用被禁用时的降级需与系统侧约定

痛点 2

昨天没做完的，今天打开就看不见了

笔记里的待办跟着它所在的那篇笔记按时间排。昨天那篇今天已经沉到列表下面，首页看不到它。用户得自己记得"我好像还有件事没做"，再往回翻，才知道漏了什么。越久以前的越翻不到。

方案

未完成的自动出现在今天，不跟着原笔记沉底

  • 没做完的待办每天自动出现在今天的列表里，并标出它是从哪天顺延过来的
  • 逾期的单独标记，一眼看出压了几天
  • 完成后从今天的列表消失，在原记录里留痕，随时可回溯

依赖 / 待定　需要一份跨笔记的待办索引；与系统待办中心的数据边界待定

痛点 3

要做的事散在四五个地方，没有一处能看全今天

笔记里的勾选框一份、系统待办一份、日历一份，还有别人在聊天里交办的。用户要在几个入口之间来回切，才能拼出今天到底要做什么。带时间的那些如果没进日历，等于没设提醒。

方案

汇到一处按今天／本周看，并与日历双向联动

  • 各来源待办汇到一处，按今天、本周看，不按来源分
  • 带时间的与系统日历双向联动，一边改另一边跟着改
  • 完成状态跨端同步：手表上点完成，手机同时更新

依赖 / 待定　与系统日历、待办中心的双向接口

痛点 4

在车上、耳机上说的，回到手机上找不到

开车时想起一件事，对着车机说了一句。到手机上翻不到，用户也不确定到底记下了没有，回头还得再记一遍。耳机、手表上说的同样如此。

方案

多端说的都进同一处，到点在手上那台设备提醒

  • 手机、车机、耳机说一句都落到同一处，多端同步
  • 到点在用户手上那台设备提醒（手机或手表），不是只响一台

依赖 / 待定　车机、耳机侧唤起小爱后的写入通道；跨端同步时延待实测

交互链路

车上说一句 → 笔记里认出是待办 → 今天要做什么一处看全 → 到点在手上的设备提醒

02

想法随记

用户自己记下的东西延伸出来的都在这里：工作上的思考、生活随记、兴趣，也包括一段时间里为同一件事做的多次记录，比如一轮访谈、一次调研。

痛点 1

工作和生活混在一条时间流里，越记越翻不动

随口记的想法按天往下排。两周后往回翻，工作上的思考、周末的随记、看到觉得有意思的东西混在一起，得一条条看才知道哪条是哪件事。记得越多，这条流越没法用。

方案

同主题的自动聚成一处并起好标题，工作与生活分开

  • 同一主题的记录攒够就聚成一处，标题自动起好（工作想法、生活随记、钓鱼、西安访谈）
  • 工作与生活不混在同一处；子分类跟着用户实际记的内容长出来
  • 判不准的先保持原样，攒够了再归，不硬归类

依赖 / 待定　预置几个还是全部按内容长出来（见最后一节）

痛点 2

想接着往下想，先得把当时那几条找回来

一个月前记过几条关于同一件事的想法，现在想接着想。搜关键词搜不出来——当时用的词跟现在想的词不一样。就算找到了，还得把几条复制出来喂给 AI，才能接着聊。

方案

点进去就是对谈，这一处的内容已经挂上了

  • 进去第一件事是接着聊，界面上显性标出已挂载了这一处的多少条内容
  • 是可持续的会话：上次聊到哪里留着，下次能接上，不是一次性问答
  • 开场先说清这段时间反复出现的是什么，用户不用自己回想

依赖 / 待定　需小爱侧支持把这一处内容作为上下文挂载并保持会话

痛点 3

自己反复在想什么，自己看不出来

同一个问题两周里提了五次，每次都是一条独立的记录。用户不会去数，也就意识不到这已经是个反复出现、一直没解决的事。零散记录里最有价值的那部分，就这么留在流里。

方案

把反复出现的点指出来，每条能回到原话

  • 一处内容里反复出现的主题、一直卡住的地方主动指出来，标出出现了几次
  • 每条结论能点回当时那句原话，不是凭空给的判断

依赖 / 待定　跨月聚合与归因效果待跑数

痛点 4

一轮访谈是七段录音，没人会一段段听回去

出差三天做了七场访谈，每场一段录音。回来要出一份总结，只能自己一段段听、一段段摘，再想办法拼到一起。等真拼完，时间已经过去很久。

方案

多次记录聚成一处，点一下落成一份，做完推送

  • 一段时间里为同一件事做的多次记录聚成一处，标题自动起好，聚好了主动推送
  • 点一下落成阶段总结、成长记录或下一步计划；默认是整理好的正文，可显性换成 PPT / PDF / Excel
  • 里面写出来的下一步能直接进待办

依赖 / 待定　形态转换走沙箱能力，本版做哪几类需圈定

03

学习备考

这个场景的链路从笔记之外就开始了：课程表在相册里被认出来、课在日历里、上课时录音。到笔记这边，要做的是把一堂堂课变成一门课。

痛点 1

最难的一步是想起来开录音

一堂课两个小时，学生经常忘了点录音，或者上到一半才想起来——前面那段就没了。这一堂课的内容从此是不完整的，后面无论怎么整理都补不回来。

方案

按课表自动录音，加端侧持续预录兜住忘记的那几分钟

  • 日历里的课程日程标为自动录音，到点自己开始，不依赖用户动手
  • 端侧低功耗持续预录，中途才点开也能接上前面那段，一堂课不缺口

依赖 / 待定　日历提供课程日程与循环规则；预录时长、功耗与存储边界待技术侧评估

痛点 2

一门课的东西散在四个地方

课上录音在笔记里，老师的课件在群里，电子教材是个下载的文件，往年真题是另一个文件。写作业或者复习时，用户要在几个应用之间来回找，还得自己记得存到哪了。

方案

一门课自动聚齐四类来源，存进来就归位

  • 课堂录音、课件、电子教材、往年真题聚到同一门课下
  • 群里发的课件、作业存下来就落到对应课程，用户不用管存到哪了
  • 两三堂课之后这门课成形，聚好了推送

依赖 / 待定　文档类内容的课程归属判定准确率待跑数

痛点 3

录了十几段音，考前不会一段段听回去

一学期十几堂课的录音都在，考前只剩两天。用户要的不是录音，也不是逐字转写，是这门课要考什么、我到底会不会。现在这一步全靠自己做。

方案

进这门课先给复习要用的东西

  • 进去是精讲、快讲、出一套卷子，不是一串课堂录音列表
  • 考点大纲、按章节、按堂次三种看法，每个考点能回到原文那一段
  • 答错的按间隔重复再考；出题只用这门课存进来的内容
  • 原始资料（录音、课件、教材、真题）退到次级入口

依赖 / 待定　能拆出判定步骤的考点占比待跑数，过低则本版先只出考点清单

痛点 4

写作业时还是得自己把课上内容翻出来

老师留的作业要结合这几堂课的内容做。用户得先找到对应那几堂课的笔记，再一边翻一边写。写完了，下次看日程也不知道这门课的作业到底交了没有。

方案

作业挂在这门课下，写的时候直接用上课上的内容

  • 存进来的作业自动识别并挂在这门课下，标出未完成
  • 写的时候能直接用上这门课的录音、课件内容
  • 完成进度回到日程里，下次看课程日程时能看到

依赖 / 待定　日历侧承接作业进度与笔记入口

04

不在这三类里的内容

旅行攻略、一次临时会议、随手收藏的资料，用户也会往笔记里存。这些不单独设计一套形态——走的是上面三个场景已经在用的同一套聚合与生成。

痛点 1

零散存下来的东西，隔几天就想不起来存过

刷到一篇成都攻略存了，隔天又存了一家店、一份交通信息。真要出发时，这几条散在时间流里，用户记不清自己都存过什么，只能一条条翻。

方案

同主题攒够了就聚成一处，判不准的先原样放着

  • 没落到三个场景里的内容，按主题聚到一起并自动起标题（一趟旅行、一次装修、一个项目）
  • 判不准的保持原样，不硬归；攒够了再归
  • 用的是三个场景同一套聚合规则，不另做一套

依赖 / 待定　存量内容补理的范围待定

痛点 2

存了一堆材料，拼成能用的东西还得自己来

攻略、店、交通都存了，但要变成一份能照着走的行程，还是得用户自己排。工作上同理：几篇记录里的数字要凑成一张报价单，只能手动抄。

方案

聚好的点一下就落成一份能用的东西

  • 点一下整理成行程、报价单、对账表或可分享的网页
  • 默认整理好的正文，可显性换形态；每项能点回原文
  • 带时间的项目可以直接进日历

依赖 / 待定　与场景二共用同一套生成与形态转换

痛点 3

原来建的文件夹和习惯不能被打乱

用户手里已经有自己建的文件夹、几百篇笔记。新的这一层如果把原来的东西挪走或者藏起来，老用户第一天就不会用了。

方案

原始内容与文件夹原样保留在「笔记」这一侧

  • 用户原来建的文件夹、单篇笔记继续在，编辑与查找方式不变
  • 加工后的那一层是新增的一侧，不影响原有使用习惯

依赖 / 待定　升级后首次进入的引导方式待定

05

由这些需求推出：交互框架要怎么变

上面四节里，用户真正打开去用的都是整理加工之后的那一份：今天要做的事、一处想法、一门课、一趟行程。原始那几条退到后面。

原来的框架只有"一篇篇笔记按时间排"这一种形态，承载不了加工后的这一层。

所以内容分两层，各自要有自己的位置。加工后那一层需要能按品类铺开、能横着看、每个格子有标题看得出里面是什么——这件事原始笔记流做不到，两者也不该挤在同一个 tab 里。

这一层怎么定对应上面哪个需求
底 tab 两个 洞察（今天的待办、一处想法、一门课、一趟行程都在这里）／笔记（原始记录与原有文件夹）。两者不混在同一个 tab。 三个场景用的都是加工后那一份；其余内容那节要求原始文件夹原样保留
洞察页的组织 按品类分栏 → 栏内横向滑动 → 每个格子是一个能直接消费的单元，标题自动起好。参照相册的组织与呈现方式。 待办按今天／本周；想法按一处主题；学习按一门课；其余按一趟一件事
格子里默认给什么 默认是整理好的正文（成本可控），能显性换成 PPT / PDF / Excel 等形态。原始那几条退到次级入口。 场景二落成阶段总结、场景三出卷、其余内容拼行程，都要能换形态
创建入口两个 一个加号建文字笔记，另一个进录音。原来的第三个按钮去掉。 记的动作只有这两类；语音与录音是三个场景的主要来源
分类只留一层 顶栏分类 + 侧边栏分类 + 底 tab 三层同时存在过于复杂。顶栏与侧边栏都收掉，分类只留洞察页内的品类分栏；原有文件夹进「笔记」tab。 品类分栏已经承担了分类，不需要再来两层
做完要推送 一处内容聚合、加工完成主动推送提醒。 七场访谈聚好、一门课成形、行程拼好，用户都不会主动回来看
06

这几处想跟你对一下

想法随记的子分类，预置还是长出来 工作想法、生活随记是预置好的固定分栏，还是全部跟着用户实际记的内容长出来（钓鱼、西安访谈这种）？预置好理解但可能空着；长出来更贴合，但新用户进来是空的。我倾向工作与生活预置两个，其余按内容长出来。
洞察页还没有内容时长什么样 新用户、或者存量用户刚升级上来，洞察页还没有格子。是给引导（记两条就能看到），还是先用存量内容补理出几个格子？这一屏必须画出来，不然上手第一眼是空的。
端侧持续预录的边界 学习备考那条链上最关键的一步。预录多长、只在课程日程时段还是常开、功耗与存储怎么控，需要先和技术侧对一个可行范围，再定交互怎么呈现。
