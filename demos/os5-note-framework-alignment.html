用户需求与交互链路

从用户记完之后真正要什么出发：三个场景各自的洞察、要做的需求、完整交互链路；最后由这些需求推出笔记的交互框架该怎么变。

2026-09-10 · 内容助手 · 对齐用

01

用户需求变了什么

同一件事在三个场景里反复出现：记的时候是零散的一条条，用的时候要的是整理好的一整份。现在中间那段整理，全靠用户自己做。

用户在做什么

"这门课我录了十几次，课件在群里，往年真题老师发过，考前得复习"

现在卡在哪

课上录音、课件、作业、真题落在不同地方。考前要自己一篇篇翻，翻完还得自己串成能复习的东西。

所以要变成

同一门课的东西自动在一起，进去就能重新讲一遍、出一套卷子自测。

用户在做什么

"想到什么随口记一条，过一个月想接着往下想"

现在卡在哪

工作的生活的混在一条时间流里往下排。一个月后想接着想，找不到当时那几条，也不记得自己反复在想什么。

所以要变成

同一个主题的自动聚到一起，进去能接着聊，聊出来的东西能落成一份。

用户在做什么

"会上记的、路上说的，都是我要做的事"

现在卡在哪

没做完的要自己抄到今天这一页。笔记里的待办、系统待办、日历是三套，得人来搬。

所以要变成

没做完的自己滚到今天，带时间的自己进日历，各端到点提醒。

三件事的共同点：用户要用的不是当时记下的那几条，而是整理加工之后的那一份。

下面按三个场景把需求和交互链路写清楚。不属于这三类的内容，走同一套聚合与生成，最后一节说。

场景一

待办日程

用户不想在笔记里读待办，只想知道现在该做什么、别错过时间。

真实场景

开车路上想起周五要给客户发方案，对着车机说一句。会上边听边记，记的话里夹着三件要做的事。

卡在哪

说完记下了，但到点没人提醒。会议记录里那三件事还埋在正文里。上周没做完的，要翻回去自己抄。

要什么

记的那一刻就被认出来是待办，自动落到待办和日历，到点在手上的设备提醒；没做完的自己往后滚。

需求要做什么依赖 / 待定
随口记待办 手机、车机、耳机说一句就记下，多端同步。原话保留在笔记里，识别出的待办单独成条。 车机、耳机侧唤起小爱后的写入通道；跨端同步时延待实测
从记录里认出待办 录音、语音、图片、手写里的待办与日程自动认出来，用户确认后落位。识别出的地点、联系人、链接分发成可点卡片。 置信度低于阈值不自动建；目标应用被禁用时的降级需与系统侧约定
一处管全 + 自己往后滚 各来源待办汇到一处；未完成的自动出现在今天，不用重抄；带时间的与系统日历双向联动，各端到点提醒，完成状态跨端同步。 与系统日历、待办中心的双向接口
交互链路

车上说一句 → 认出是待办 → 洞察里看到今天要做什么 → 到点在手表提醒 → 没做完的明天自己还在

场景二

想法随记

用户自己记下的内容延伸出来的东西都在这里：工作上的思考、生活随记、兴趣，也包括一段时间里为一件事做的多次记录（比如一轮访谈、一次调研）。

真实场景

两周里陆陆续续记了九条工作上的想法。出差三天做了七场访谈，每场一段录音。

卡在哪

都在时间流里按天往下排，工作生活混着。想接着往下想，得先把当时那几条找出来；七场访谈是七篇录音，没人会一篇篇听回去。

要什么

同主题的自动聚成一处并起好标题；进去能直接接着聊，聊完能落成一份阶段总结或计划。

需求要做什么依赖 / 待定
按主题自动聚，工作生活分开 同主题的记录攒够就聚成一处并自动起标题（工作想法 / 生活随记 / 兴趣 / 一轮访谈）。工作与生活不混在同一处。子分类跟着用户实际记的内容长出来。 预置几个还是全部按内容长出来，待定（见最后一节）
进去就是对谈 点进去第一件事是接着聊，界面上显性标出已挂载了这一处的多少条内容，是可持续的会话，不是一次问答。开场先说清这段时间反复出现的是什么。 需小爱侧支持把这一处内容作为上下文挂载并保持会话
聊完能落成一份 聊出来的结论能直接落成阶段总结、成长记录、下一步计划；默认是整理好的正文，可以显性换成 PPT / PDF / Excel。每条结论能点回原话那一段。 跨月聚合与归因效果待跑数；形态转换走沙箱能力

场景三

学习备考

这个场景的链路从笔记之外就开始了：课程表在相册里被认出来、课在日历里、上课时录音。到笔记这边，是把一堂堂课变成一门课。

真实场景

写数学作业时，桌上要同时摊开课本、卷子、草稿纸和这门课的课堂笔记；写完塞回书包，第二天再来一遍。

卡在哪

一门课的东西散在各处：录音在笔记、课件在群里、真题是老师发的文件。最难的是上课经常忘记开录音，录了也是一堂一堂的散音频。

要什么

一门课自动聚齐四类来源；进去能重新讲一遍、出一套卷子；作业能结合课上内容写。

需求要做什么依赖 / 待定
按课表自动录音 日历里的课程日程标为自动录音，到点自己开始；配合端侧低功耗持续预录，用户忘了点、中途才点，前面那段也能接上，一堂课不缺口。 日历 提供课程日程与循环规则；端侧预录的功耗与存储边界待评估
一门课自动聚齐四类来源 课堂录音、课件、电子教材、往年真题聚到同一门课下。老师发的课件、群里发的作业，用户存下来就落到对应课程，不用他管存到哪。两三堂课后这门课成形，做完推送。 文档类内容的课程归属判定准确率待跑数
进去能复习：精讲 / 快讲 / 出卷 不是一串课堂录音列表。进去先给重新讲一遍（精讲 / 快讲）和出一套卷子自测；考点大纲 / 按章节 / 按堂次三种看法，每个考点能回到原文那一段。作业可以结合课上内容一起写。 能拆出判定步骤的考点占比待跑数，过低则本版先只出考点清单

05

不在这三类里的内容

旅行攻略、一次临时会议、随手收藏的资料，用户也会往笔记里存。这些不单独设计一套形态——它们走的是上面三个场景已经在用的同一套聚合与生成，攒够了一样能聚成一处、一样能落成一份。

需求要做什么依赖 / 待定
同主题攒够就聚成一处 没落到三个场景里的内容，按主题聚到一起并自动起标题（比如一次装修、一趟旅行、一个项目）。判不准的保持原样，不硬归，攒够了再归。 与三个场景共用同一套聚合规则，不另做一套

06

由这些需求推出：笔记的交互框架要怎么变

上面四节里，用户真正打开去用的都是整理加工之后的那一份：一门课、一处想法、今天要做的事、一趟行程。原始那几条退到后面。原来的框架承载不了这一层——它只有"一篇篇笔记按时间排"这一种形态。

所以内容分两层，各自要有自己的位置：整理加工后可以直接消费的那一层，和用户记下的原始内容那一层。

加工后的那一层需要能按品类铺开、能横着看、每个格子有标题看得出里面是什么——原始笔记流做不到这件事，两者也不该挤在同一个 tab 里。

这一层怎么定为什么（对应上面哪一节）
底 tab 两个 洞察（一门课、一处想法、今天的待办、一趟行程都在这里）／笔记（原始记录与原有文件夹）。两者不混在同一个 tab。 三个场景要用的都是加工后那一份；原始内容仍要能编辑能翻
洞察页的组织 按品类分栏 → 栏内横向滑动 → 每个格子是一个能直接消费的单元，标题自动起好。参照相册的组织与呈现方式。 学习备考按一门课一个格子；想法随记按一处主题一个格子；待办按今天／本周
格子里默认给什么 默认是整理好的正文（成本可控），能显性换成 PPT / PDF / Excel 等形态。原始那几条退到次级入口。 场景二落成阶段总结、场景三出卷、其余内容拼行程，都要能换形态
创建入口两个 一个加号建文字笔记，另一个进录音。原来的第三个按钮去掉。 记的动作只有这两类；语音与录音是三个场景的主要来源
分类只留一层 顶栏分类 + 侧边栏分类 + 底 tab 三层同时存在过于复杂。顶栏与侧边栏都收掉，分类只留洞察页内的品类分栏；原有文件夹进「笔记」tab。 品类分栏已经承担了分类，不需要再来两层

这几处想跟你对一下

想法随记的子分类，预置还是长出来 工作想法、生活随记是预置好的固定分栏，还是全部跟着用户实际记的内容长出来（钓鱼、西安访谈这种）？预置好理解但可能空着；长出来更贴合，但新用户进来洞察页是空的。我倾向工作与生活预置两个，其余按内容长出来。
洞察页还没有内容时长什么样 新用户、或者存量用户刚升级上来，洞察页还没有格子。是给引导（记两条就能看到）、还是先用存量内容补理出几个格子？这一屏必须画出来，不然上手第一眼是空的。
端侧持续预录的边界 学习备考那条链上最关键的一步。预录多长、只在课程日程时段还是常开、功耗与存储怎么控，需要和技术侧先对一个可行范围，再定交互怎么呈现。
