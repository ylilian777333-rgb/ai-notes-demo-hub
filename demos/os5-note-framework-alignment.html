01

待办日程

已定：进合集

用户不在笔记里读待办。他要的只有一件事：现在该做什么，别错过。

根本需求 现在该做什么，别错过

待办不是一类要阅读的内容，是一份要执行的清单。用户不需要「能记待办的地方」，需要打开就等于当下状态、且维护成本不落在自己身上。

子需求 L1 自动认出是待办

我在笔记里写下一件要做的事，系统就该知道这是待办，不用我再去别处录一遍。

P1
子需求 L2 一个地方看全今天

打开就是今天全部要做的事，昨天没做完的自己排到最前面。

P2 · P3
子需求 L3 知道这件事从哪来

看到一条待办，一眼知道它是哪次记录里说的，点一下能回到当时那句话。

P4
子需求 L4 换个设备接着处理

手机上随口记的，坐到电脑前打开就在，改完再拿手机看还是改完的样子。

P5
子需求 L1 自动认出是待办

在笔记里写下一件要做的事，系统就该知道这是待办

1 个痛点
P1

记在笔记正文里的待办，从来没被当成待办

现象

开会时顺手写下“下周五之前把方案发给老王”，它就是正文里的一行字。到了周五没有任何提醒。用户要么自己再去待办应用录一遍，要么就漏了。语音转写出来的那一大段里，这类句子更是彻底埋着。

用户真实需求

我写下来的时候就当我在安排一件事，别让我再录第二遍。

我们做什么

正文与转写里自动抽取待办项，用户确认后成立。

交互链路

正文与转写里自动抽取待办项，用户确认后成立

说一句 → 笔记里认出待办并带来源 → 首页待办卡出现 → 待办中心到点提醒

→ → →
方案要点
  • 正文、语音转写、图片、手写里的待办句自动抽出来，连带时间一起。
  • 抽出来的每一条保留回原句的链接，不脱离上下文。
  • 抽错了能直接取消这一条，不影响原文。
  • 置信度低于阈值只提示、不自动建立。
子需求 L2 一个地方看全今天

打开就是今天全部要做的事，昨天没做完的自己排到最前面

2 个痛点
P2

待办散在笔记正文、待办中心、日历三处，没有统一的今天

现象

笔记里勾选框一份，系统待办一份，日历里还有一份带时间的。用户要在三个地方来回切，才拼得出今天到底要做什么。哪件事在哪儿，他自己也记不清。

用户真实需求

给我一个地方，打开就是今天全部要做的事。

我们做什么

今天这一屏只做汇总，不再造第四份数据。

交互链路

今天这一屏只做汇总，不再造第四份数据

三处各一份 → 今天一处看全并标出来源 → 日历里同一条 → 写外部前先确认

→ → →
方案要点
  • 笔记认出的、待办中心里的、日历里带时间的，汇到同一处看。
  • 数据仍在原来的地方，笔记不另存一份，避免三处不一致。
  • 要写回待办中心或日历时，先让用户确认，不静默写外部。
P3

没做完的会沉底，第二天不会自己出现

现象

待办跟着它所在的那篇笔记按时间排。昨天那篇今天已经沉到列表下面，用户打开首页看不到它。要靠自己想起“我好像还有件事”，再往回翻。越久以前的越翻不到。

用户真实需求

没做完的事，明天该主动站到我面前，而不是等我想起来。

我们做什么

自动结转到今天并排在最前，标出顺延了几天。

交互链路

自动结转到今天并排在最前，标出顺延了几天

昨天两条没做完 → 今天自动结转排最前 → 连续顺延给出口 → 首页待办卡跟着变

→ → →
方案要点
  • 未完成的每天自动结转到今天，排在新事项前面。
  • 标出它是从哪天顺延过来的、压了几天。
  • 连续顺延多次的给出口：改期，或者标记不做了。
子需求 L3 知道这件事从哪来

一眼知道这条待办是哪次记录里说的，点一下能回到当时那句话

1 个痛点
P4

看到那条待办，想不起当初为什么记它

现象

“确认报价口径”——这是哪个客户、当时在哪次会上说的？一条干巴巴的待办脱离了当时的上下文，用户看着它得先花时间回忆，甚至干脆放着不动。

用户真实需求

让我一眼知道这件事的来处，必要时能回去看当时说了什么。

我们做什么

每条待办带来源，能回到被记下的那一句。

交互链路

每条待办带来源，能回到被记下的那一句

待办上看到来源 → 回到被记下的那一句 → 录音跳到那个时间点

→ →
方案要点
  • 待办上带来源标识：哪篇笔记、哪次录音、哪天。
  • 点一下回到被记下的那一句原话，不是只跳到笔记开头。
  • 来自录音的，直接跳到录音里对应的时间点；转写需保留句级时间戳。
子需求 L4 换个设备接着处理

手机上随口记的，坐到电脑前打开就在，改完手机上也是改完的样子

1 个痛点
P5

手机上记的待办，到电脑和平板上处理不了

现象

路上用手机随口记了三件要办的事，回到工位真正要处理的是电脑。现在电脑端看不到手机上抽出来的待办，勾掉的状态也不回传。用户只能对着手机屏幕再在电脑上敲一遍，或者干脆整天低头看手机处理。平板上写作业、开会记录同理，写完的东西回不到手机的今天。

用户真实需求

在哪个设备上记的不重要，我在手边这台上就能接着处理，改完别的设备上也是改完的样子。

我们做什么

手机、平板、电脑共用同一份待办，任意一端改完，其他端跟着变。

交互链路

三端同一份待办：哪台在手边就用哪台，勾掉一次全部生效

手机上随口记 → 三端同一份 → 电脑上批量处理 → 手机再看已是处理完的状态

→ → →
方案要点
  • 待办只有一份，手机、平板、电脑读的是同一份数据，不做三份各自的清单。
  • 完成、顺延、改时间在任意一端做完，其他端跟着变，不需要用户手动刷。
  • 来源信息跨端保留：在电脑上也能点回手机那次录音的对应位置。
  • 离线改过的内容在联网后合并，同一条被两端改过时以最后一次为准并保留另一份记录。
  • 电脑和平板上不重做一套抽取，抽取仍在存进来的那一端完成，其余端只做展示和处理。
02

想法随记

访谈属于这里，不单独立品类

用户自己记下的内容延伸出来的都在这里：工作上的思考、生活随记、兴趣，以及一段时间里为同一件事做的多次记录。

根本需求 看清自己的思考足迹，并知道下一步做什么

想法的价值不在单条，在同一件事的多次记录攒起来之后。用户不会回头手动整理，所以聚合、命名、推送都得由系统完成。

子需求 L1 工作和生活不混在一起

工作的事和私人的事别排在同一条时间流里，但我记的时候也不想先选分类。

P6
子需求 L2 同一件事自动聚成一页

为一件事记过很多次，这些记录该自己聚到一页上，不用我回头手动整理。

P7
子需求 L3 聚起来的能直接用

打开这一页先告诉我结论和下一步；想清楚的东西要能直接变成我交得出去的那一份。

P8 · P9
子需求 L1 工作和生活不混在一起

两类事别排在同一条时间流里，但记的时候不用先选分类

1 个痛点
P6

工作和生活混在同一条时间流里

现象

随口记的东西按天往下排。周一的排期思考、周末看到的一家店、晚上的一句感想挨在一起。两周后往回翻，得一条条看才知道哪条是哪件事。工作场合翻到私人内容也不合适。

用户真实需求

工作和生活别放在一起，我记的时候也不想先选分类。

我们做什么

品类按语境固定，记进来自动归类。

交互链路

品类按语境固定，记进来自动归类

随口记一条 → 自动归到工作 → 首页想法卡 → 想法品类页里工作和生活分开

→ → →
方案要点
  • 想法下面固定分工作、生活、兴趣，不让用户自己建。
  • 记完自动归到对应的一栏，归错了在卡上一下能改。
  • 用户不需要在记之前做任何选择。
子需求 L2 同一件事自动聚成一页

为一件事记过很多次，这些记录自己聚到一页上，不用回头手动整理

1 个痛点
P7

同一件事记了很多次，这些记录之间没有任何关系

现象

一个月里为同一件事记了二十几条，散在二十几篇里。用户自己不会回头把它们并到一起，也不会为此建文件夹。结果是记得越多，越没有一处能看到这件事的全貌。

用户真实需求

同一件事的记录自己聚到一起，我不想手动整理。

我们做什么

自动聚成一个合集并自动起名，聚好了推送。

交互链路

自动聚成一个合集并自动起名，聚好了推送；打开之后给什么，按品类定

散在多篇 → 后台聚成合集并起名 → 推送告诉你 → 打开这一页，内容按品类给

→ → → → →
不同品类，这一页给的东西不一样
品类聚成一页之后给什么一眼能看到的
工作 · 一件事的推进反复想的是什么、卡在哪、下一步做什么6 条记录 / 4 个月跨度 / 2 条结论
生活 · 宠物日常按时间排的成长记录、指标变化、该做的事到期提醒时间线 / 体重 4.2 公斤 / 驱虫下周到期
生活 · 想去的地方按城市归好的清单，带位置和当时为什么想去12 个地点 / 3 个城市 / 可直接导航
方案要点
  • 同一件事的多次记录聚成一个合集，名字自动起好。
  • 聚好主动推送，不靠用户回来发现。
  • 页面骨架三段不变（摘要、成品、原文），中间那块成品按品类换，不套同一个模板。
  • 品类给什么由品类定义决定：工作给结论，宠物日常给时间线和提醒，地点类给清单和导航。
  • 判不准的先保持原样，不硬凑一个合集。
子需求 L3 聚起来的能直接用

打开先给结论和下一步，想清楚的能直接变成交得出去的那一份

2 个痛点
P8

东西聚起来了，用户不知道在这儿能干什么

现象

就算把二十几条相关记录摆在一起，用户面对的还是一堆自己写过的字。想接着往下想，得自己先看一遍、再把要点复制出来喂给 AI。反过来，只给一个空的问答框也没用——用户不知道该问什么，也懒得把背景再说一遍。多数人到这一步就停了。

用户真实需求

先让我看到这些记录汇出来的结论，再让我从这个结论接着聊下去。

我们做什么

第一屏给聚出来的结论，结论下面就是对谈入口，进去是接着这些结论往下聊。

交互链路

先给聚合好的结论，再从结论接着聊：对谈入口在第一屏，进去内容已挂上、不用重新交代背景

进合集先看到结论 → 点结论下面的「接着聊」 → 对谈里带着这 24 条往下推 → 结论和下一步能进待办

→ → →
方案要点
  • 顺序是先结论、后对谈：第一屏是这些记录汇出来的结论和下一步，用户先知道这儿有什么。
  • 对谈入口在结论正下方，是一个显性的入口，不是散在页面里的「问小爱」按钮。
  • 进对谈时内容已挂上并显性标出挂了多少条，用户不用重新交代背景。
  • 开场由 AI 基于聚合结论先抛一个判断和几个可点的追问，不给空的问答框。
  • 会话是持续的：这次聊到哪里留着，下次进来接着说。
  • 结论和对谈里定下来的事都能加进待办，并带上来源。
P9

聊出来的结论拿不出去

现象

对谈里理清楚了，但要发给同事、要在会上讲，还是得自己重新排成一份文档或几页 PPT。笔记里的东西最后停在纯文本上。

用户真实需求

理清楚的东西要能直接变成我拿得出手的那一份。

我们做什么

默认给正文，需要时显性转成别的形态。

交互链路

默认给正文，需要时显性转成别的形态

默认正文 → 显性选形态 → 生成中 → 拿得出手的一份

→ →
方案要点
  • 合集里默认给整理好的正文，不预先生成 PPT 那些，成本控住。
  • 需要时一键转成 PPT / PDF / Excel，由用户发起。
  • 转出来的每条结论能点回原话；里面的下一步能直接进待办。
03

学习备考

链路从笔记之外开始

这个场景的链路从笔记之外开始：课程表在相册里被认出来、课在日历里、上课时录音。笔记这边要做的是把一堂堂课变成一门课。

根本需求 这门课考什么，我到底会不会

用户不要录音，也不要逐字转写。他要的是把一堂堂课变成一门课，然后在这门课上直接看考点、做题、确认自己会了没有。

子需求 L1 一门课的材料自动齐

属于这门课的录音、课件、教材、真题，存的时候不用想放哪儿，要复习时都在一起；该录音的时候自己录上。

P10 · P11
子需求 L2 考前知道先看哪里

别把材料摊给我，直接告诉我这门课考什么、先看哪一块，再给几道题让我确认自己会了没有。

P12
子需求 L3 作业和这门课连着

写作业时课上的材料就在手边，不用自己找；写完的进度回到这门课里，不用另记一笔。

P13
链路 跨功能怎么串

这条链从笔记之外开始，笔记只负责最后两段

5 段 · 4 个功能
链路

从拍一张课程表，到合集里长出这门课

整条链

站在用户视角是一条链：相册认出课程表 → 日历有课程日程 → 小爱到点提醒 → 笔记自动录音 → 合集里长出这门课

相册 → 日历 → 小爱 → 笔记（自动录音） → 笔记（合集成形并推送）

→ → → →
这条链的口径
  • 前三段不在笔记这一侧：相册负责认出课程表，日历负责课程日程的专属样式，小爱负责到点提醒。
  • 笔记负责第 04、05 段：按课表自动录音、端侧常录接住忘记的那段，两三堂之后在合集里成形并推送。
  • 任一段缺失都不阻断：课程表没被认出来，用户手动建一门课也能进第 04 段；只是链路变长。
  • 这条链上笔记不重复建日程，课程日程只有日历一份，笔记读的是同一份。
子需求 L1 一门课的材料自动齐

存的时候不用想放哪儿，该录音的时候自己录上

2 个痛点
P10

一门课的材料散在四五个应用里

现象

课上录音在笔记，老师的课件在群里，电子教材是下载的文件，往年真题是另一个文件。存的时候还要想存到哪个文件夹。复习时在几个应用之间来回找，找的时间比看的时间长。

用户真实需求

属于这门课的东西，我存的时候不用管去哪，要用的时候都在一起。

我们做什么

四类来源自动归位：保存即归位，不弹文件夹选择。

交互链路

四类来源自动归位：保存即归位，不弹文件夹选择

群里的课件分享到笔记 → 直接落到这门课 → 首页课程卡 → 一门课里四类来源齐了

→ → →
方案要点
  • 课堂录音、课件、电子教材、往年真题自动归到同一门课下。
  • 群里发的文件存下来直接落到对应课程，不弹「存到哪个文件夹」。
  • 归错了在这门课页面上一下能改。
P11

十次有三次忘了开录音，而且忘了就永久没了

现象

一堂课两小时，学生经常忘记点录音，或者上到一半才想起来。跟其他遗漏不一样：这个是不可逆的，那段课的内容再也补不回来，后面所有整理都建立在一段缺口上。

用户真实需求

该录的时候自己录上，我忘了也别真的丢。

我们做什么

课程日程到点自动录音，端侧常录最近几分钟接上忘记的那段。

交互链路

课程日程到点自动录音，端侧常录最近几分钟接上忘记的那段

上课前提醒 → 到点自己开始录 → 忘了点也能接上前面 → 录完自动归位并整理好

→ → →
方案要点
  • 日历里的课程日程标为自动录音，循环生效，到点自己开始。
  • 端侧低功耗常录最近几分钟，中途才点开也能接上前面那段。
  • 录完自动归到这门课，不用用户操作。

04

三类之外的内容

判出来才展示，判不出来不展示

前面三章是本期要做完整方案的三类。用户存进来的东西不止这三类，剩下的不能没有归宿，也不该为每一类都单独做一套页面。这一节说清剩下的怎么接。

4.1 三种归宿

每条存进来的内容只走这三条路之一，不存在第四种情况

3 条路径
路径 A

判出是三类之一

待办日程、想法主题、课程这三类，走前面三章的完整方案：有自己的聚合页，也有按品类定好的成品页。这三类是本期投入做深的部分。

路径 B

判出是预设类目之一

不在三类里，但判出属于预设类目库里的某一类，进通用合集页。这一页对所有类目是同一套结构：一段摘要、一个按类目定的成品、下面是原文列表。类目判出来了才出现在首页，判不出来就不出现。

路径 C

判不准

原样留在笔记列表里。不强行归到某一类，也不弹窗让用户自己选。同一类攒到能成一页的量，再回到路径 B 生成合集。

为什么是「判出来才展示」，不是「先建后填」

  • 类目由系统预先定好，不由用户创建。P6 和 P10 已经说明，让用户自己想清楚该建哪个分类这条路走不通，分类层级越多存得越少。
  • 没判出来的类目在界面上不存在。预设二三十个类目，用户只会看到自己真的有内容的那几个，不会打开一堆空页面。
  • 判不出来不是错误状态。判不准就原样留着，不给用户任何处理负担，攒够了再自动成页。
4.2 预设类目库

一条内容判出属于哪个类目，决定它进哪种页面、页面上出现什么成品

12 类

预设类目库

类目是我们预先定义的，不开放给用户创建。判定依据决定什么样的内容算这一类，归宿决定它进哪一种页面，成品决定这一页上用户能直接拿走什么。

类目判定依据归宿这一页给什么成品状态
待办日程出现时间、地点、待办动作核心品类 · 完整方案一处看全的日程与待办本期做深
想法主题同一件事的多次零散记录核心品类 · 完整方案主题合集与可以直接交的成稿本期做深
课程课程表、课堂录音、课件、作业核心品类 · 完整方案一门课的考点与自测本期做深
访谈调研多人对话录音，问答结构明显通用合集页访谈纪要与观点清单本期通用
旅行行程连续日期 + 地点 + 票据凭证通用合集页按天排好的行程单本期通用
阅读摘录书名、页码、划线段落通用合集页一本书的摘录合集本期通用
项目复盘同一项目名下的过程记录通用合集页时间线与结论本期通用
育儿记录固定对象 + 连续时间的短记录通用合集页成长时间线本期通用

健康记录体检项、指标值、用药记录通用合集页指标趋势定义先留
未分类三条判定都不成立留在笔记列表不生成成品，攒够再聚暂不成页

类目库怎么往下扩

新增一个类目只需要定三件事：判定依据（什么内容算这一类）、成品定义（这一页给用户什么）、字段映射（抽出来的字段填到成品的哪里）。不需要新做一套页面，也不需要改前面的抽取和判定。这是把通用类目做成一套东西、而不是一个个专项的原因。

4.3 通用合集页

所有非核心类目共用的一套页面结构，成品按类目换

一套结构
4.3

一页三段：摘要、成品、原文

交互链路

判出来的类目出现在首页 → 进去就是整理好的一页 → 原文在下面，改不了的东西一条不动

存进来 → 判出类目 → 首页出现这个合集 → 摘要 + 成品 + 原文列表

→ → →
方案要点
  • 通用合集页只有一套结构：摘要、一个成品、原文列表，所有类目共用。
  • 成品按类目定：访谈是纪要，旅行是按天行程，阅读是摘录合集，账单是按月汇总。
  • 原文一条不改。合集是在原文之上生成的一层，点进去还是原来那条笔记。
  • 没判出来的类目在首页上不出现，用户不会看到空的合集。
  • 卡证与密码这一类涉及敏感内容，进合集页需要单独加锁，本期只定义不放量。
4.4 一条内容存进来之后怎么走

三类核心品类和通用类目走同一条路，只有最后一步不一样

3 步
第一步 先看这条内容里有什么

不管存进来的是照片、录音还是手写，都先把里面的时间、地点、人、金额、要做的事挑出来。这一步不判断它属于哪一类，所有内容走的是同一套。

第二步 再判断它属于哪一类

拿第一步挑出来的东西去比类目库：是待办日程、想法主题、课程，就走前面三章的完整方案；是访谈、旅行、阅读这些，就进通用合集页；比不出来的到这里停住。

第三步 按这一类该给的样子摆出来

同样一张车票，在旅行行程里要落到某一天，在账单流水里要算进这个月的支出。摆成什么样由类目定，所以新增一个类目，只需要说清这一步怎么摆。

三个实际例子

同一条路，三条不同的内容走下来分别是什么结果。第三条走到第二步就停了，这是允许的结果，不是出错。

存进来的是什么第一步挑出什么第二步判成哪一类第三步摆成什么样
一张高铁票截图10 月 1 日、成都东、G1978、票面金额旅行行程进「成都 3 天」的行程单，落在 10 月 1 日那一天
一段 30 分钟的双人录音两个人轮流说话、有问有答、反复提到续费和价格访谈调研进访谈合集，生成纪要和观点清单，标出几个人提到同一件事
一张写着 B2-137 的停车位照片一串编号，没有时间、没有人、没有要做的事比不出来不生成任何东西，原样留在笔记列表里

为什么要拆成三步

  • 前两步只做一次，三类和通用类共用。不是三类走一条路、通用类另走一条，挑内容和判类目是同一份能力。
  • 加类目的成本只落在第三步。新增一类不碰前两步，只要说清这一类要摆成什么样。
  • 停在第二步是允许的。判不准就不往下走，内容原样留在笔记列表，不会给用户生成一个错的东西。
05

交互框架

需求推出来的结构

框架放在最后，是因为它不是设计目标。前面 13 个痛点要落地，现在的结构就承不住，改结构是结果不是起点。这一节说清现在卡在哪、改成什么样、每一层因为哪些痛点存在。

5.1 现状与改后

差别就一句话：成品层放到原始层前面

对比
现状

首页只有原始层

打开笔记是一列笔记。不管存进来的是录音、拍照还是手写，都以「一条笔记」的形式并排放着，彼此没有关系。用户要用的时候，得自己想起来它在哪、自己翻、自己把几条拼成一个能用的东西。

一列笔记文件夹靠手建成品要自己整理要用先翻找
改后

成品层在前，原始层退到后面

打开先看到的是按品类整理好的状态，和已经可以直接用的成品。原始的一条条笔记一条不少，位置后移，需要溯源的时候进得去。用户消费的是成品，不是原始记录。

5.2 为什么要动

不是为了改版，是前面的痛点在同一个地方反复撞

3 条
1
13 个痛点里有 7 个卡在同一处

P1、P2、P3、P6、P7、P10、P12 的现象各不相同，但卡在同一处：内容已经在笔记里了，用户要用的时候找不到、也拼不起来。这不是某个功能没做，是首页只有原始层这一件事造成的。补功能补不掉，只能改结构。

2
用户要消费的不是某一篇笔记

P12 要的是这门课考什么，P8 要的是一份能直接交出去的东西，P9 要的是这件事到底想到哪一步了。这三个都不对应某一条笔记，对应的是笔记之上的一层成品。现在的结构里没有这一层，用户只能自己在脑子里合成。

3
让用户自己分类这条路走不通

P6 和 P10 说的是同一件事：分类层级越多，用户越不愿意存，存了也不记得存在哪。所以品类得由系统判定，不能让用户先想清楚再存。用户自己建的文件夹继续保留，但不能是主路径。

5.3 四层结构

每一层都对得上前面的痛点，没有一层是凭空加的

4 层 + 3 处旁挂
第一层 首页 · 品类状态总览

打开就是几个品类的当前状态：今天要做什么、这门课到哪了、最近在想什么。只出现判出来的品类，每张卡只说当前状态和一个动作。

因为 P1 · P2 · P3：存进来的东西不该等用户想起来才被看见
第二层 品类聚合页

一个品类下面的全部内容收在一起，上面是这个品类的整理结果，下面是属于它的原始内容。品类固定，用户不建也不选。

因为 P6 · P7 · P10：同一件事的记录散在各处，用户拼不起来
第三层 成品页

用户真正要消费的那一页：一处看全的日程、主题合集与可以交的成稿、一门课的考点与自测、通用类目的合集。这一层是内容被真正消费的地方。

因为 P8 · P9 · P12：用户要的不是某一条笔记，是笔记之上的那个东西
第四层 对谈与形态转换

在成品页上直接追问、改写、换形态：转成表格、转成提纲、转成自测题。进来就已经挂好这一页的全部材料，不用再选范围，也不用离开这一页。

因为 P4 · P9 · P13：想改一下就得从头交代一遍背景
旁挂 全部笔记

原始的一条条笔记按时间排，一条不少。溯源、搜索、看原话都走这里。

原样保留，位置后移
旁挂 我建的文件夹

用户自己建的文件夹继续在，习惯用的人不受影响。但存的时候不再要求先选文件夹。

兼容存量用户，不作为主路径
入口 创建与保存

录音、拍照、分享、手写这几个入口不变。区别是存的时候不弹分类，归位在后台做。

因为 P10 · P11：存的动作越轻，用户才会存

相册式
