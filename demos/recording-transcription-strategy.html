核心问题

BEFORE (现状)

用户录 10 秒语音 → 等 20-40 秒出结果

AI开thinking深度推理，占总耗时 70-80%
模型同时做：判断意图 + 规划结构 + 选择格式 + 生成输出

AFTER (优化后)

用户录 10 秒语音 → 3-5 秒出结构化卡片

本地判断意图(0ms) + 关thinking + 模型只做填槽提取

策略核心逻辑（三步）

STEP 1 - 本地意图预分类
关键词匹配，判断 TODO / SCHEDULE / GENERAL
耗时 0ms，纯规则引擎
STEP 2 - 按置信度选路径
HIGH → 关thinking快速路径 | LOW → 开thinking深度路径
判断依据 = "我是否确定用户要什么"
STEP 3 - 专用 Prompt 精准调用
每种意图配固定JSON schema，模型只需填槽
关thinking 3-5秒 / 开thinking 10-30秒

核心设计：判断依据是"我是否确定用户要什么"，而不是"用户说了多少字"。200字购物清单（意图明确）走快速路径；7字模糊表达（意图不清）走thinking路径。

引擎路径决策

录音速记场景 固定走 LocalEngine（直接调 mimo-pro API），不走 OSbot。

  • OSbot session建立 + skill加载就要 7 秒，LLM还没开始推理
  • OSbot 有工具白名单限制，会导致流程中断

超时机制

不用固定超时。改为 首 token 超时：

  • 发请求后 15 秒内无任何 streaming 响应 → 判超时
  • 一旦收到首个 token → 不再超时，等完整结果返回

用户感知时间线

第 0 秒
录音完成，显示波形 + "正在转录..."
第 2 秒
ASR完成，立即展示转录文本（用户已看到内容）
第 3 秒
文本下方出现 shimmer 占位符 + "AI分析中..."
第 5 秒
shimmer 替换为结构化卡片（待办/日程），渐入动画

即使 AI 实际耗时 10 秒，用户在第 2 秒就看到了自己说的内容，感知等待从 10 秒降至 2 秒。

本地意图预分类器

纯规则引擎，0ms 完成。关键词命中 → 输出 (意图类型, 置信度)

TODO 待办 — 强信号词

记一下 提醒我 别忘了 待办 要做的

命中 2+ 个 → TODO + LOW置信度

SCHEDULE 日程 — 强信号词

安排 日程 行程 预约 约了

命中 + 有时间词 → SCHEDULE + HIGH置信度

GENERAL 通用

无法匹配上述任何信号

→ GENERAL + HIGH（直接做文本整理）

产品定义：待办 vs 日程

类型 定义 触发词 展示格式
待办 用户要做的事，有 checkbox 可完成 做/买/记/提醒/别忘了 - [ ] 项目（可打勾）
日程 确定的时间安排，不可打勾 安排/约/出发/航班/行程规划 时间 + 事件
模糊时 无法判断 — 默认走待办

关键规则：有"记一下/提醒我/别忘了" = 强制 TODO。只有"安排/预约/行程规划"才走 SCHEDULE。模糊时默认 TODO 而非 SCHEDULE。

置信度路由逻辑

置信度 触发条件 thinking 耗时 输出
HIGH 命中强信号关键词 关 3-5秒 待办/日程/整理文本
LOW 无法确定意图 开 10-30秒 LLM自主判断+生成

降级与容错机制

原则：永远不让用户干等。ASR转录完就先展示文字，AI结果是增量覆盖上去的。

LLM 返回结果

解析失败 / 超时

尝试顺序方法
1直接 JSON 解析原始输出

全部失败降级为纯文本笔记 (Fallback)

录音速记的边界

录音速记只做"识别 + 结构化输出"，不做"执行动作"。

  • 禁止调用 calendar__create_event 等执行类工具
  • 用户要加日历 → 由卡片按钮手动触发
  • AI 只负责理解和整理，不负责操作

真机测试已发现的问题（2026-05-20）

基于开发提供的 debug 包真机测试发现，按优先级排序

P0
超时机制过于激进 — 用户录音后显示"音频分析失败"
修复：去掉固定8秒超时，改为首token超时15秒。收到首个token后不再超时。
P0
所有内容都生成日程卡片 — "记一下明天开会"被判为schedule
修复：有"记一下/提醒我/别忘了"= 强制 TODO。模糊时默认 TODO 而非 SCHEDULE。
P0
卡片需退出再进入才展示 — WebView错过更新事件
修复：AI生成卡片后主动push刷新给WebView；WebView未就绪时缓存结果，ready后立即渲染。
P1
AI擅自创建系统日历事件 — 调用calendar工具被拒导致中断
修复：录音速记场景禁止调用执行类工具。只做识别+结构化，不做执行。
P1
待办vs日程产品定义缺失 — 开发不知道何时出待办、何时出日程
修复：新增明确定义。待办=用户要做的事(可打勾)；日程=确定的时间安排(有时间线)。
P1
两条引擎路径行为不一致 — 有时走OSbot(慢)有时走LocalEngine(快)
修复：录音速记场景固定走 LocalEngine（直接调mimo-pro API），不走OSbot。
P2
一条录音触发3次LLM — 速记+归档+标签串行执行
修复：文件夹归档和标签分类延迟到退出编辑器后后台执行，不阻塞录音结果。

验证标准（开发前必做）

调用 mimo-pro API (thinking=false, temperature=0.1) 测试 5 条用例：

  • "记一下明天下午三点开会"
  • "帮我记一下周末要买牛奶和面包还有鸡蛋"
  • "提醒我下周一给张总打电话"
  • "别忘了晚上八点的瑜伽课"
  • "今天下午讨论了三个议题第一个是发版计划"

判定：5条中4条输出合法JSON且字段正确 → 方案可行，进入 Phase 1
